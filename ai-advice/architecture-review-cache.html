Redis 缓存清除"假删"——按前缀模式清除完全失效

Bug-01
AutoClearCacheAspect.java:64 AutoClearCacheAspect.java:70-71 RedisConstant.java
问题
// 用户端写入缓存时：key 是带 categoryId 的
String key = RedisConstant.DISH_CATEGORY_KEY_PREFIX + categoryId; // "dish:category:1"
redisTemplate.opsForValue().set(key, json, ...);

// 切面清除时：
redisTemplate.delete(RedisConstant.DISH_CATEGORY_KEY_PREFIX); // = 删 "dish:category:" ← key 不存在！

Redis 的 delete(key) 是精确匹配，不支持通配符。切面试图删除字面量 "dish:category:"（根本不存在这个 key），而实际菜品缓存是 "dish:category:1"、"dish:category:2"……所以菜品、套餐缓存永远不会被真正清除！管理端修改了菜品，用户端看到的还是旧数据。

修复代码
private void cleanUserDishCache() {
    Set keys = redisTemplate.keys(RedisConstant.DISH_CATEGORY_KEY_PREFIX + "*");
    if (keys != null && !keys.isEmpty()) {
        redisTemplate.delete(keys);
        log.info("已清除菜品缓存 keys={}", keys);
    }
}

private void cleanUserCategoryCache() {
    // 同样删掉硬编码的 + "1" + "2"，改成通删
    Set keys = redisTemplate.keys(RedisConstant.CATEGORY_TYPE_KEY_PREFIX + "*");
    Set allKeys = new HashSet<>(keys);
    allKeys.add(RedisConstant.CATEGORY_LIST_KEY);
    redisTemplate.delete(allKeys);
}

缓存知识散落在 4 个文件——缺乏 locality

Arch-01
RedisConstant.java AutoClearCacheAspect.java user/CategoryServiceImpl.java user/DishServiceImpl.java
问题
一个缓存 key 的完整生命周期散在 4 个文件里：
  • RedisConstant 定义 key 前缀字符串
  • user/CategoryServiceImpl 知道怎么拼 key（prefix + type），知道怎么序列化解序列化（ObjectMapper 手动 JSON）
  • user/DishServiceImpl 又重复了一遍一模一样的 JSON 读写样板代码
  • AutoClearCacheAspect 维护另一份 key 清单来决定删什么

改一个 key（比如 "dish:category:" → "menu:dish:"）要同时改 Constant、Aspect、两个 User Service 的 key 拼接。知识不聚内 = 改一处漏三处。

方案
抽一个 CacheManager 作为单一真相源： 
@Component
public class CacheManager {
    private final RedisTemplate redis;
    private final ObjectMapper mapper;

    // 读侧：封装 key 拼 + 序列化 + 缓存降级
    public List getCategoryList(Integer type) { ... }
    public List getDishList(Long categoryId) { ... }

    // 写侧：封装模式匹配 + 批量删除
    public void invalidate(String pattern) {
        Set keys = redis.keys(pattern + "*");
        if (keys != null) redis.delete(keys);
    }
}

User Service 只管 cacheManager.getDishList(categoryId)；切面只管 cacheManager.invalidate(cacheType.pattern())。所有 Redis 细节收一处。

CacheType switch 每次加类型都要改切面

Arch-03
CacheType.java AutoClearCacheAspect.java:35-50
方案
让枚举携带清除逻辑： 
public enum CacheType {
    CATEGORY("category:*"),
    DISH("dish:category:*"),
    SETMEAL("setmeal:*"),
    SHOP_STATUS("shop:status");

    private final String pattern;
    CacheType(String pattern) { this.pattern = pattern; }
    public String pattern() { return pattern; }
}

// 切面简化成一行：
String pattern = cacheType.pattern() + "*"; // 或者枚举里直接写完整 pattern
Set keys = redisTemplate.keys(pattern);
redisTemplate.delete(keys);

新增缓存类型（比如 ORDER）只要改枚举加一行，切面代码不动。

Speculative

Spring Cache vs 手动缓存 — 想清楚一个问题

Spec-01
你在 RedisConfiguration 开了 @EnableCaching，但所有 Service 都在手动调 RedisTemplate + ObjectMapper。这本身不是问题——手动可以精细控制过期时间、降级、损坏数据清理——但需要想清楚：

是有意选择手动？（比如不同类型数据要不同过期时间、需要自定义序列化、需要降级） → 那就保留手动，但收敛到 CacheManager 里。

还是没来得及换成 Spring Cache？ → 换成 @Cacheable / @CacheEvict 会消灭大量样板代码，而且跟你的 @AutoClearCache 注解本质上做的是同一件事（按类型清除缓存）。

两种都可以，但要主动选择，别让 @EnableCaching 在那开着而你全手动——那就是一个迷惑信号。

🎯 Top Recommendation — 先修 Bug，再谈架构

第一步（必须立即修）：把 AutoClearCacheAspect 里所有 redisTemplate.delete(单 key) 改成 redisTemplate.delete(keys("prefix:*"))。这是整个缓存清除机制的核心 bug——当前它是静默失效的，没有任何报错，最危险的那种。

第二步（顺手修）：切入点表达式去掉 impl 字面量，去掉 admin CategoryServiceImpl 里没用的 RedisTemplate 注入。都是一分钟的事。

第三步（再深化）：抽 CacheManager + 让 CacheType 携带清除 pattern。不急，加下一个缓存类型时顺手做。
